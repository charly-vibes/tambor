## BZ1 — Streaming finance dashboard (tambor-54j.13, lane feat/bz1-dashboard)

App: `src/examples/bench/stream-dashboard.ts` (+ the pure data half
`src/examples/bench/stream-tickers.ts`) — demo `stream-dashboard` in
the gallery SPA; scenarios `bz1-build`, `bz1-stream-naive`,
`bz1-stream-frame` in `tests/e2e/bench-scenarios.ts`; results
`benchmarks/results/bz1-*.json`.

Simulated stream: 500 tickers (deterministic syms/prices), each row
drawn with price, change-vs-open and an 8-level text-block sparkline
over a bounded 24-point history ring; a top-5-by-|change| book line
(full sort per derivation); 80-message bursts (BURST — one 60 fps
frame's worth of the row's ≈5k msg/s). Chrome 156.0.8078.4, CPU
throttled ×4, 3 runs × 12 ops per scenario
(+1 untimed warmup op each), production bundle. 13 bursts per run ⇒
the summary line reads `msgs 1040` — the expectedText no-op guard.

### Expected-vs-actual failure of the naive mode — CONFIRMED (T)

The BZ1 row predicts "one dispatch + full re-derive per message".
Measured (median per timed op, CPU ×4):

| scenario | median ms | p90 ms | mean ms |
|---|---|---|---|
| bz1-build (one 500-row derive + draw) | 370 | 400 | 370 |
| bz1-stream-naive (80 dispatches / op) | **7 812** | 9 626 | 8 155 |
| bz1-stream-frame (1 dispatch / op) | **383** | 439 | 398 |

The naive pump (`naivePump`) calls `app.dispatch` once per message —
each dispatch schedules its own repaint, so per click the wire pays
80 full view derivations (drawn rAF repaints) plus, through the
mount's dispatch wrapper, 80 synchronous full draws, on top of the
route's own two derivations and draw. Net: **~20.4× the frame-coalesced
op** (7 812 / 383), ≈98 ms per message-dispatch vs ≈4.8 ms per message
amortised in the frame op. The frame op costs the same as bz1-build
(383 vs 370 ms — one derive + one draw of the 500-row view), i.e.
coalescing reduces the burst's view cost to a single frame's worth.

Both modes leave IDENTICAL state — `applyBurst(s, k) ≡ k sequential
applyOneMsg` applications is a pinned contract
(tests/bench-stream-dashboard.test.ts) — so the delta is dispatch
shape, not data divergence. The naive number is not a strawman: the
pump is the natural per-message wiring (`route` per incoming quote),
exactly what an uncoalesced websocket handler does.

### H2 verdict

H2 ("event-rate workloads need coalescing to one dispatch per frame;
the rAF guard may defer without coalescing") — **supported at BZ1
scale (T)**. The rAF guard coalesces nothing here: 80 queued repaint
callbacks each re-derive; the guard defers, it does not dedupe.

### Candidates not built in this lane (D/O)

- **Canvas sparklines** (§4.8 canvas layer taking data by reference):
  rejected for scope — the text-block sparkline already makes each
  row a real drawn node (the per-row view cost the bench measures);
  a canvas layer would remove the rows from the measured wire
  entirely and needs the §4.8 canvas-seam component first.
- **Per-row memo**: unnecessary at this scale once coalescing lands —
  the frame op re-derives all 500 rows once per frame for 436 ms;
  per-row memo is the follow-up if the frame cost itself must drop
  (BZ4's memoised derived paths lane covers the mechanism).

### Harness notes (genuine gaps, minimal fixes)

- `gallery.html` fixture nav now carries `overflow-x: auto` — with 13
  demos the nav overflows the 800px fixture viewport; Playwright's
  click on a fully-offscreen nav button scrolled the PAGE right and
  put the pinned stage (x=8) offscreen-left, so every scripted stage
  click missed (found by the bz1-stream-naive op clicks, all no-ops).
  The nav scrolls within itself; the page and the stage origin never
  move (a flex-wrap variant was tried first and rejected: the extra
  nav rows pushed the tall logo demo's controls below the fold and
  broke its mobile-380 Clear-world click).
- `bench-apps.bench.ts` gains the `drawnOps` op-click wire (same gap
  the log-stream lane filed): the in-process replay measures labels at
  `text.length` while the bundle configures real text metrics, so the
  non-first buttons' replay points ("Stream naive" at x≈40) landed
  inside the drawn "Build 500" button — scenarios declare `drawnOps`
  to click the drawn button's live DOM box instead.
## BZ5 — Log/metrics streaming (tambor-54j.17, lane feat/bz5-logstream)

App: `src/examples/bench/log-stream.ts` — demo `log-stream` in the
gallery SPA; scenarios `log-stream-naive-append`,
`log-stream-ring-append`, `log-stream-search` in
`tests/e2e/bench-scenarios.ts`; results `benchmarks/results/log-stream-*.json`.

Simulated stream: 250-line ingest batches (≈0.15 s of a 100k
lines/min stream); deterministic lines (error every 10th id, warn
every 5th); ring capacity 2000; fixed-height drawn window of the
newest 50 ring lines; search term "error" over the drawn text.
Chrome 156.0.8078.4, CPU throttled ×4, 15 runs × 12 ops per scenario
(unthrottled warmup + 1 untimed warmup op), production bundle.

### Expected-vs-actual failure of the naive mode — CONFIRMED (T)

The BZ5 row predicts unbounded append (memory growth) and O(n) work
per op. Measured, median per timed op by cycle position (the corpus
grows by 250 lines per op, 250 → 3250 over a run):

| cycle op | corpus lines | median ms |
|---|---|---|
| 1 | 250 | 200 |
| 4 | 1000 | 408 |
| 7 | 1750 | 707 |
| 10 | 2500 | 1107 |
| 12 | 3000 | 1025 |

Scenario totals: **median 636 ms, p90 1054 ms, mean 653 ms** — a clean
monotone climb, ≈ 70 ms of added per-op cost per extra 1000 naive
lines. Every op pays the full immutable copy of the ever-growing array
(H3) plus the one-pass histogram re-derive over it, and the drawn log
is unbounded (all 3250 lines drawn — the DOM grows with the stream).
`expectedText "all 3250"` pins that the app really ingested 13 batches.

### Candidate: bounded ring buffer + fixed-height window — MEASURED, GREEN (T)

`ringAppendOp` keeps only the newest 2000 lines (drop-oldest) and the
view draws only the newest 50 (fixed height). Same wire, same op
count, same batch size:

| | naive | ring (candidate) |
|---|---|---|
| median | 636 ms | **83 ms** |
| p90 | 1054 ms | 83.8 ms |
| per-op slope | +70 ms / 1000 lines | **flat** (82–83 ms every cycle position) |

The candidate is **flat across the entire run** — per-op cost is
independent of how much the stream has ingested, exactly the §4.8
constraint "state holds windows and summaries, never the raw stream".
`expectedText "kept 2000"` pins the drop-oldest invariant.

### Candidate: main-thread search — MEASURED (T)

`log-stream-search` cycles ingest-then-search over both corpora
(Search all over the naive corpus, Search ring over the ring). Per-op
median grows ~linearly with the scanned corpus for both (200 ms at 250
lines → 635 ms at 1500 lines), because the scan is a full pass over
plain data each op. Scenario totals: median 387 ms, p90 585 ms. The
ring's 2000-line cap bounds the ring side of this curve by
construction (the scenario exits before the cap binds); the naive side
is unbounded.

### Candidate: Worker filtering/aggregation — REJECTED, with numbers (D on T data)

The Worker precedent (turtle worker, tambor-y9d.10) makes off-thread
search buildable, but the data argues against it here:

- The measured op cost (83–636 ms) is dominated by the whole-view
  re-derive + DOM write + paint of a 300×300 surface, not by the scan:
  the scan itself is a single `includes` pass over ≤3250 short strings
  (sub-millisecond unthrottled at this size). Moving the scan to a
  Worker does not touch the dominant cost.
- A Worker round trip pays `postMessage` structured clone of the
  corpus (O(corpus) per query) plus worker startup/scheduling — that
  overhead scales exactly like the scan it replaces at window sizes
  ≤ RING_CAPACITY, and wins only when the corpus is the naive
  unbounded one (≥10⁵ lines per the SLO sketch). But the right fix for
  an unbounded corpus is bounding the state (the ring, measured above
  at a flat 83 ms), not off-threading the scan over it.
- Rejection outcome: keep filtering in-process; a Worker is only
  worth revisiting if a corpus beyond the ring is ever retained
  (e.g. aggregate-only summaries shipped to a Worker while the ring
  stays the drawn window).

### Harness finding surfaced by this lane (O/T — follow-up flagged)

While bringing the ring scenario green, a systematic wire flaw fell
out: the harness resolves op points from the in-process replay view,
whose measure is `defaultMeasure` (`text.length` per label), while the
bundle configures real text metrics. The drawn buttons are therefore
several times wider than the replay model, and **a non-first button's
replay point lands inside the drawn first button's box** — verified
with keyed-table: the replay point for "Replace 10%" clicks "Build
1000" (the table is rebuilt, `!!!` never appears). Existing scenarios
that click non-first buttons were guarded so that the first button's
effect keeps them green (dashboard `count 500` after Seed;
save-restore `items 5000` after Build), i.e. their guards cannot
detect the misroute — likely measuring the wrong op. This lane added a
minimal, opt-in wire to the harness (`drawnOps` in the Scenario shape:
click the drawn button's live DOM box via drive.ts `clickDrawnText`)
and used it for all three log-stream scenarios. The other scenarios
are untouched; re-pinning them on `drawnOps` (or widening the replay
measure to match the bundle) is the flagged follow-up.

### SLO reading (D)

Against the §4.6 sketch (ingest 50k lines/s, search < 200 ms with a
Worker): the bounded candidate sustains a 250-line batch + full
re-derive + paint in 83 ms at CPU ×4 — ≈ 3k lines/s per frame at
throttled-clock, growing linearly with real clock speed; ingest scale
is bounded by ring capacity, memory constant. The naive mode fails the
sketch at ~1.7k lines/s already (636 ms per 250-line batch at
corpus 3250).

Provenance: lane tambor-54j.17 · app + scenarios + results in-tree ·
grades as marked.

## BZ2 — Interactive plots (tambor-54j.14, lane feat/bz2-plots)

App: `src/examples/bench/plot-points.ts` (+ the view half
`src/examples/bench/plots.ts`) — demo `plots` in the gallery SPA;
scenarios `bz2-plots-build`, `bz2-pan-naive`, `bz2-pan-tx`,
`bz2-zoom-naive`, `bz2-zoom-tx` in `tests/e2e/bench-scenarios.ts`;
results `benchmarks/results/bz2-*.json`.

App shape: two LINKED charts (series A blue, series B red) over one
100k-point shared x domain (`plot-points.ts` — both charts read the
SAME array, no per-chart copy); the window is 40k points, one pan
slides 10k, zoom halves (floor 10k). Charts draw the standard
decimated line: per-band min/max verticals on a fixed 50-point band
grid — 800 bands/chart at w 40000, 200/chart at the 10k floor. Chrome
156.0.8078.4, CPU throttled ×4, 5 runs × 12 ops per scenario (+1
untimed warmup op), production bundle; 13 clicks per run ⇒ the summary
line reads `win 10000 w 40000 pans 13` (pan) / `win 0 w 10000 pans 13`
(zoom) — the expectedText no-op guards, full-line pinned.

### Expected-vs-actual failure of the naive mode — NOT CONFIRMED (T)

The BZ2 row predicts "re-deriving while panning; copying point data"
fails. Measured (median per timed op, CPU ×4, per-cycle medians flat
within noise in every scenario):

| scenario | op work (data side) | median ms | p90 ms |
|---|---|---|---|
| bz2-plots-build (Load: 100k points + 2 full-domain indexes + first draw) | 100k makePoint + 2×100k index pass | 645 | 717 |
| bz2-pan-naive (copy 40k window + re-derive 2×800 bands) | 3.3 ms* | 606 | 755 |
| bz2-pan-tx (slice 2×800 index bands, by reference) | 0.03 ms* | 617 | 734 |
| bz2-zoom-naive (copy + re-derive 2×200 bands) | 0.8 ms* | 183 | 243 |
| bz2-zoom-tx (slice 2×200 index bands) | 0.03 ms* | 183 | 237 |

\* in-process node timings, unthrottled (×4 ⇒ ≈13 ms throttled).

The predicted failure does NOT show: naive and transform pan are the
same median (606 vs 617 ms — the 3 ms data-side delta is 13 ms at ×4,
beneath the ±100 ms run noise), and zoom is likewise flat (183 vs
183 ms). Why: a tambor dispatch re-derives the whole view and redraws
the whole decimated chart on EVERY op regardless of how the state got
there, so the op cost is the drawn tree, not the data pass. The drawn
tree is the scaling law: pan draws 1600 path nodes/op (2 charts × 800
bands) → ≈606 ms; zoom draws 400 → ≈183 ms — a 3.3× cost ratio for a
4× drawn-node ratio. Even the Load op's 18.6 ms of data work is
invisible under the 645 ms first draw.

### Candidate: precomputed band index + pan/zoom as transform + data by reference — CORRECT, but NOT the perf lever on this wire (T/D)

Built and pinned: the index (one 2×100k pass at Load) makes pan/zoom a
slice of small band objects that stay BY REFERENCE — the 100k points
are never touched, never copied, memory flat; the naive ≡ transform
drawn-geometry identity is a contract test (tests/bench-plots.test.ts,
the BZ1 "same final state, different shape" pattern). The data says
adopt it for correctness and cost-shape (3.3 ms → 0.03 ms data-side,
naive's 40k window copy gone), but honestly: on this wire it buys
nothing visible, because the per-op cost is the re-derive + re-draw
the framework performs anyway. Adopted as the app's built mode.

### Candidate: canvas layer taking data by reference — POINTED AT BY THE DATA, rejected for scope (D on T data)

This lane's numbers are the evidence the §4.8 canvas-seam candidate
needs: the op cost scales with drawn nodes (1600 → 606 ms, 400 → 183
ms), not with data size (3 ms of pass noise-level). A canvas layer
taking the points by reference would remove the per-op DOM re-write of
1600 nodes entirely — the one lever that could move pan toward
pointer-rate (60+ Hz). Rejected for this lane's scope: it needs the
§4.8 canvas seam (turtle's seg-normalization path is the nearest
precedent) and would remove the drawn chart from the measured wire
entirely (the BZ1 sparkline note's objection applies).

### Candidate: decimation — ADOPTED, it is what makes 100k points buildable at all (T)

100k drawn path nodes is not a chart, it is the failure mode (turtle's
20k is already a stress test). The 50-point band grid decimates to
1600 drawn nodes with pinned per-band min/max correctness against an
independent recomputation. The zoom cycle doubles the drawn density at
the floor (200 bands/chart over 10k points = 50 points per band) at
183 ms/op — decimation is what keeps zoom bounded.

### Brush + pointer-rate pan — not built (U/D)

Brush and true pointer-drag pan (60+ Hz event streams) need a drag
chain the click-op harness does not replay; at the measured 606 ms/op,
a 60 Hz pan stream would queue ≈36 frames/op — the canvas-layer
candidate above is the response the data points at. Flagged as the
BZ2 follow-up.

Provenance: lane tambor-54j.14 · app + scenarios + results in-tree ·

## BZ7 — Spreadsheet (tambor-54j.19, lane feat/bz7-spreadsheet)

App: `src/examples/bench/spreadsheet.ts` (+ the pure model half
`src/examples/bench/spreadsheet-sheet.ts`) — demo `spreadsheet` in the
gallery SPA; scenarios `bz7-build`, `bz7-edit-naive`, `bz7-edit-graph`
in `tests/e2e/bench-scenarios.ts`; results
`benchmarks/results/bz7-*.json`.

The model: a **1M-cell logical grid** (10 000 × 100) whose defined
cells are a sparse plain-data map — 10 000 literals in column A plus
**90 000 three-ref formulas** in columns B..J (`=A4+A5+A6` shape: every
formula sums the three clamped neighbours of the previous column, so
the formula grid is a DAG with fan-out 3 per column and the whole
sheet is one wide pyramid). Only the first 24 × 10 window is drawn
(the keyed-table viewport pattern — the 1M is the logical model, never
DOM). State is plain data: `cells` (contents), `values` (computed),
`deps` (the reverse dependency index, built once at seed time —
editing a literal never changes its outgoing refs) and an `edits`
counter. Both timed ops apply the **same** literal edit (+3 to the
cycled row, rows 1..13 — the drawn window) and leave the **same**
final state; the drawn status line pins `edits 13 sum 160480317064` —
a dropped edit, a misroute or a misrecompute changes it (and
`tests/bench-spreadsheet.test.ts` pins naive-vs-graph deep equality,
the closure property against an independently rebuilt index, and
evaluator correctness against hand-computed convolution weights).
Chrome 156.0.8078.4, CPU throttled ×4, 5 runs × 12 timed ops (+1
untimed warmup) per scenario, production bundle.

### Expected-vs-actual failure of the naive mode — CONFIRMED (T)

The BZ7 row predicts "recomputing everything" as the hazard. Measured
(median per timed op, CPU ×4):

| scenario | median ms | p25 / p75 | p90 |
|---|---|---|---|
| bz7-build (Seed: 100k cells + 90k-eval sweep + dep index) | 1 900 | 1 866 / 1 927 | 1 971 |
| bz7-edit-naive (full recompute per edit) | **1 633** | 1 616 / 1 665 | 1 683 |
| bz7-edit-graph (dependency-graph recompute) | **1 401** | 1 383 / 1 433 | 1 453 |

The naive per-op recompute is **flat across the run** (first-third
median 1 633, last-third 1 633): it re-sweeps all 90 000 formulas
every edit regardless of what the edit touched — the hazard is
constant, not growing, because the sheet's defined size is fixed. The
unthrottled in-page split (playwright profile, no throttle): the
naive op costs ~125 ms and the graph op ~70 ms per click — the
90 000-eval sweep is the only term that differs.

### Candidate: dependency graph over derived paths — ADOPTED (T)

The candidate (the §4.3 "dependency graph over derived paths", cf. B9
notebook §4.4) recomputes only the edited cell's transitive dependents:
BFS over the reverse dep index collects the closure (54–100 cells for
rows 1..13 — edges span one column, so the closure is a widening
triangle, not the whole sheet), then evaluates it in column order
(topological). Same final state as the full sweep — deep-equality
pinned in the unit tests, and the bench's `expectedText` checksum is
**identical across both scenarios** (`edits 13 sum 160480317064`), so
the measured ops are verified equivalent, not merely faster.

The win, 233 ms/op median (1 633 → 1 401, −14%), is exactly the
recompute term: it is the **only** per-op cost that scales with
formula count. Unthrottled, the naive sweep evaluates all 90 000
formulas per edit (~55 ms in-page) while the closure walk evaluates
54–100 (~0.1 ms); the rest of the op is a shared floor (the plain-data
state copy of the 100k-entry cells/values maps + the click wire — see
the harness finding below) that both strategies pay. The candidate is
therefore flat in the formula count while the naive sweep grows
linearly with it — a sheet with 10× the defined formulas would
multiply only the naive term. Adoption is on data, and the closure
discipline costs nothing in correctness — both ops leave bit-identical
state.

### Harness finding surfaced by this lane (O/T — follow-up flagged)

Profiling the ops with a no-op blank click (outside any handler)
showed the **click-wire floor itself scales with the app's state
size**: 18–27 ms per blank click on an empty sheet, 247–254 ms on the
seeded 100k-cell sheet — unthrottled, with no repaint involved (the
paint wait is a separate ~25–35 ms). The event router's click path
therefore walks (or materialises) something proportional to the
defined cells on every pointer event, app work or not. This dilutes
every large-state app's per-op median (the BZ4/BZ6/BZ7 rows all sit on
large plain state) and is worth a dedicated lane: it is corpus
machinery (`event-bubble`/hit-testing), not bench-harness wiring, so
it was not touched here.

### SLO reading (D)

Against a spreadsheet interaction bar of "edit → settle under one
frame budget" the naive mode fails decisively at any realistic
defined-cell count: 1 633 ms/op at 90k formulas (CPU ×4), scaling
linearly with the formula count. The adopted candidate holds 1 401
ms/op at the same model — of which ~1 100 ms is the shared click-wire
floor + state copy, i.e. the recompute itself is ~300 ms throttled and
stays flat as formulas grow. With the corpus click-path fix
(flag above) the same app would sit near the todo app's 83 ms floor.

Provenance: lane tambor-54j.19 · app + scenarios + results in-tree ·
grades as marked.

## BZ3 — Whiteboard (tambor-54j.15, lane feat/bz3-whiteboard)

App: `src/examples/bench/whiteboard.ts` (+ the pure scene-data half
`src/examples/bench/whiteboard-scene.ts`) — demo `whiteboard` in the
gallery SPA; scenarios `bz3-seed`, `bz3-drag-naive`, `bz3-drag-log`,
`bz3-drag-grid`, `bz3-undo`, `bz3-resize`, `bz3-cursor-naive`,
`bz3-cursor-frame` in `tests/e2e/bench-scenarios-bz.ts`; results
`benchmarks/results/bz3-*.json`.

Scene: 10k shapes on a 12px grid over a 1200×1200 world (sizes 24–30px,
so tiling is gap-free), drawn as the ~700-shape viewport window at
world (500,500) — real rectangle nodes, re-derived from the full 10k
array on every dispatch. Every op is an ordinary update intent; the
summary line `shapes 10000 drags D resizes R undos U msgs M sum S`
guards each scenario (checksum is an exact integer fold over the
scene — identical across variants, pinned
`tests/bench-whiteboard.test.ts`). Drags consume one probe per click
from a fixed 16-probe list (a run never exhausts a probe's coverage).
Chrome 156.0.8078.4, CPU throttled ×4, 5 runs × 12 timed ops (+1
untimed warmup) per scenario, production bundle.

### Expected-vs-actual: O(n) copies per op — CONFIRMED, small at 10k (T)

The BZ3 row predicts "O(n) array copies" as the drag/undo hazard. The
naive drag checkpoints the whole scene (a per-object deep copy of all
10k shapes) onto the undo stack per op; the candidate records ONE old
rect. Measured (median per timed op, CPU ×4):

| scenario | median ms | p25 / p75 | p90 |
|---|---|---|---|
| bz3-seed (10k scene + bucket index + ~700-rect draw) | 345 | 315 / 368 | 383 |
| bz3-drag-naive (snapshot history) | **313** | 299 / 330 | 369 |
| bz3-drag-log (op-log history) | **300** | 284 / 331 | 365 |
| bz3-drag-grid (op-log + maintained bucket index) | **314** | 296 / 332 | 367 |
| bz3-undo (drag+undo cycle, op-log) | 311 | 288 / 333 | 386 |
| bz3-resize (linear hit-test + grow + op-log) | 310 | 294 / 340 | 377 |
| bz3-cursor-naive (80 dispatches / op) | **6 505** | 6 419 / 6 589 | 6 695 |
| bz3-cursor-frame (1 folded dispatch / op) | **300** | 284 / 332 | 354 |

The snapshot term is real but small at this scale: **+13 ms/op median
(313 vs 300, +4.4%)**, flat across the run (first-third 314, last-third
315 — the copy cost is O(scene), not O(history)). All drag variants
leave IDENTICAL state — `dragNaive ≡ dragLog ≡ dragGrid` after 13 ops
is deep-equality-pinned, and the checksum on every drag scenario's
guard line is the same value — so the delta is pure work shape. The
shared floor is ~300 ms/op: the click wire + the full-scene view
re-derive (~700 rects walked from 10k) + the draw, paid by every
scenario including the folded cursor burst.

### Hit-testing: linear 10k vs grid-bucket — NOT a per-op cost at this scale (T, the 54j.10 evidence)

The row's second hazard, "linear hit-testing", is **not confirmed as an
end-to-end per-op cost at 10k shapes**: the grid-bucket variant
(one ~50-cell lookup, <200 members, maintained through the drag) is
**not faster** than the linear 10k scan — 314 vs 300 ms, i.e. the
index's per-drag re-registration ≈ cancels its hit-test saving, and
both deltas sit inside the p25–p75 overlap. In-process, a 10k-shape
containment scan is tens of µs — under 5% of a click op even throttled
×4. The hit-testing cost that actually scales in this corpus is the
**event router's click-path walk over the drawn surface**, which the
BZ7 lane already measured scaling with app size (18–27 ms empty →
247–254 ms at 100k cells) — a whiteboard's per-click floor (~300 ms at
10k scene + ~700 drawn nodes) is the same finding, not the app-level
scan. **For tambor-54j.10 (spatial-index component)**: (a) the evidence
here says an app-level spatial index pays for itself only when
hit-testing runs per pointer-move sample (hover/drag at 60 Hz), not on
discrete click ops; (b) the index must be maintained THROUGH edits
(`indexMove` re-registers the moved shape — the maintenance term is
what cancelled the win); (c) the bench pair (bz3-drag-log vs
bz3-drag-grid) plus `hitLinear`/`hitIndex` in whiteboard-scene.ts is
the ready-made baseline for that lane's measurements.

### Candidate: persistent collections (cherry seam) — REJECTED on data at 10k (D on T data)

The op-log candidate already removes the per-op scene copy; what
remains is the ONE immutable rebuild of the 10k shapes array every
variant pays (the move's `map`, the log-undo's restore `map`). A
persistent collection would make that O(log n), but the rebuild term
is **not measurable against the ~300 ms shared floor** (log ≡ grid ≡
frame within noise), and the snapshot term it would also remove is
+13 ms/op — a 4% win that a persistent-structure dependency and its
interop cost would buy. Rejected at 10k shapes; the data does say the
copy slope is O(scene), so the verdict flips if scenes grow ~10× or if
undo becomes an interactive-latency-critical path with the click-wire
floor fixed.

### Candidate: scene-vs-interaction layers — POINTED AT BY THE DATA, not built (D on T data)

The folded cursor burst costs exactly the drag floor (300 vs 300 ms):
even though cursors touch 8 tiny markers, the whole ~700-rect scene is
re-derived and redrawn because the view is one pure function of one
state — the interaction layer (cursors) is fused with the scene layer.
A scene/interaction split (redraw cursors without re-deriving shapes)
would cut the folded op below the floor by the scene-derive term, but
that needs component-level memoization/layer support the corpus does
not have yet — recorded as the candidate's evidence, not built here.

### Candidate: coalesced remote cursors — ADOPTED, the BZ1 prior reproduces (T)

One dispatch per cursor message over the 80-message burst costs
**6 505 ms/op; folding the burst into ONE update intent costs 300 ms —
21.7×**, matching BZ1's 20.4× per-message-dispatch prior on a different
app shape (here the per-message work is a full ~700-rect scene
re-derive + draw, flat across the run: 6 566 → 6 515 first/last third).
Both ops leave identical state (`naiveMsgOp ≡ frameOp` fold is
deep-equality-pinned; `msgs 1040` + the untouched-scene checksum guard
both scenarios). Coalescing to one dispatch per frame is the adopted
shape for any remote-cursor/multiplayer feed on this corpus.

### Native text-input bridge — not exercised (U)

The §4.3 candidate list's native text-input bridge addresses text

### SLO reading (D)

Against a whiteboard interaction bar of "drag settles under one frame
budget", the measured floor (~300 ms/op at CPU ×4, of which the

## BZ4 — Jira-like tracker (tambor-54j.16, lane feat/bz4-tracker)

App: `src/examples/bench/tracker.ts` (+ the pure model half
`src/examples/bench/tracker-board.ts`) — demo `tracker` in the gallery
SPA; scenarios `bz4-build`, `bz4-move-naive`, `bz4-move-window`,
`bz4-filter-naive`, `bz4-filter-memo`, `bz4-edit` in
`tests/e2e/bench-scenarios-bz.ts`; results
`benchmarks/results/bz4-*.json`.

Board: 5 000 issues in five columns (1 000 each), 2 500 open,
seeded deterministically (`issue i` in column i % 5, open when i is
even). Drag-drop is simulated as the move-one op the harness replays
as a click (issue `moves % 5000` one column right); the filter toggles
"open only"; the optimistic edit applies the local write and settles
the clean ack in one op. Per-column id indexes (`columns`,
`openCols`) are memoised derived paths living IN state (the
spreadsheet's dependency-index precedent), maintained incrementally by
every mutating op. One status line
(`tracker … cols … open … moves … edits … filter … rev …`) is the
no-op guard; its per-column counts, counters and revision checksum
change exactly when an op lands. Chrome 156.0.8078.4, CPU throttled
×4, 5 runs × 12 ops per scenario (+1 untimed warmup), production
bundle. 13 ops per run ⇒ `moves 13` / `edits 13` / odd-toggle
`filter open` on the line.

### Expected-vs-actual failure of the naive board — CONFIRMED (T)

The BZ4 row predicts "rendering every row" as the hazard. Measured
(median per timed op, CPU ×4):

| scenario | drawn rows/op | median ms | p90 ms | mean ms |
|---|---|---|---|---|
| bz4-build (one seed + window draw) | 40 | 67 | 67 | 64 |
| bz4-move-naive (move + draw ALL rows) | **5 000** | **1 408** | 1 765 | 1 479 |
| bz4-move-window (move + window draw) | 40 | **67** | 67 | 65 |
| bz4-filter-naive (toggle + full rescan) | 40 | 66.6 | 67 | 64 |
| bz4-filter-memo (toggle + memo read) | 40 | 66.5 | 67 | 63 |
| bz4-edit (optimistic edit + reconcile) | 40 | 66.6 | 67 | 66 |

The virtual-window candidate is **21.2× the naive board op**
(1 408 / 67) — the naive op draws all 5 000 issue rows per click and
the delta over the window op is ~1 341 ms of pure draw cost, stable
across cycle positions (1 312–1 738 ms). The window op costs the same
as the build op (67 vs 67 ms — one derive + one draw of the 40-row
board), i.e. the virtual list reduces the move's view cost to a
single frame's worth, exactly the keyed-table precedent's prediction.

Correctness is pinned, not eyeballed: after the same 13-move cycle the
naive and window boards are deep-equal on every state field (the
contract test also pins that the naive full draw, window-sliced, IS
the candidate's draw, and the identical `cols 999 1000 1000 1001 1000
open 2500 moves 13` guard line), so the delta is draw shape, not data
divergence.

### Candidate: memoised derived paths for filters — NOT the perf lever at 5k (T), adopted structurally (D)

The BZ4 row predicts "recomputed filters" as a hazard. Measured: the
naive toggle rescans all 5 000 issues per op (a single bucketing pass,
~5 000 pushes) and the memo toggle reads the maintained indexes
(zero recompute) — **66.57 vs 66.52 ms median, a 0.05 ms delta
(< 0.1%), inside run-to-run noise**. The recomputed filter is not
measurable on this wire at 5k issues: the fixed ~66 ms per-op cost is
the double view derive + drawn-DOM sync of the board itself, and a
single-pass O(n) scan over plain data is ~0.3 ms throttled. The §4.3
hazard is real asymptotically but only at issue counts (or scan
complexities) far above this bench's 5k — at 5k the DRAW, not the
recompute, is the cost.

Verdict: the memo indexes are adopted anyway (they are what bounds
every mutating op to the two touched boundary entries — the
incremental-maintenance contract is pinned), but the lane rejects the
claim that memoising the filter is the BZ4 perf lever on this wire.
The lever is the virtual list.

### Candidate: optimistic edits + clean-ack reconcile — MEASURED (T); conflict outcomes DEFERRED (U)

`bz4-edit` measures the optimistic write + ack settle at 66.6 ms —
identical to the window-board baseline (the edit's model work is two
title computations + one version bump, sub-millisecond; the measured
cost is the board derive + draw). The clean-ack wire is pinned by
contract tests (title settles to `issue <id> r<version>`, revision
checksum moves, indexes untouched). The §4.3 candidate "wanna outcomes
for conflicts" — what the board shows when the server ack DISAGREES
with the optimistic state — is OUT of harness scope and is deferred to
the wanna tracker; this bench pins only the conflict-free path.

## BZ6 — Smalltalk-like environment (tambor-54j.18, lane feat/bz6-environment)

App: `src/examples/bench/environment.ts` (+ the pure model half
`src/examples/bench/environment-model.ts`) — demo `environment` in the
gallery SPA; scenarios `bz6-build`, `bz6-edit-naive`, `bz6-edit-fold`,
`bz6-rewind-replay`, `bz6-rewind-ckpt` in
`tests/e2e/bench-scenarios-bz.ts`; results
`benchmarks/results/bz6-*.json`.

Environment: 100 000 logical objects in a sparse id→object table (the
spreadsheet's viewport pattern — the 24-entry inspector window is all
that is drawn), each object an 8-ivar plain record; one folded summary
line per window entry (the logo demo's fold-per-repaint pattern, at
inspector scale). The edit history is an IMPLICIT log — entry n edits
object `n % 100000`'s field `n % 8` by +3, a pure function of n — so
replay re-applies every entry honestly without storing 100k entries.
Seed builds the table + a 4 096-entry history with checkpoint
snapshots (immutable table references) every 1 024 entries. All four
timed ops are ordinary update intents guarded by one status line
(`objs … hist … rewinds … sum …`): the checksum covers the window's
folded lines, untouched by the timed edits, so every strategy pair
must read the SAME line. Contract tests
(`tests/bench-environment.test.ts`) pin naive≡fold and
replay≡ckpt state equality plus both probes' round-trip property.
Chrome 156.0.8078.4, CPU throttled ×4, 5 runs × 12 ops per scenario
(+1 untimed warmup), production bundle.

### Expected-vs-actual failure of the naive environment — SPLIT VERDICT (T)

The §4.3 row predicts "re-folding all entries each repaint (as the
Logo demo does)" as the failure, with huge trees and long history as
the stress. Measured (median per timed op, CPU ×4):

| scenario | op | median ms | p90 ms | mean ms |
|---|---|---|---|---|
| bz6-build (seed 100k + 4096-entry history) | one seed | 175.2 | 233.4 | — |
| bz6-edit-naive (edit + re-fold ALL 24 entries) | edit | 83.23 | 84.15 | 81.13 |
| bz6-edit-fold (edit + re-fold 1 entry) | edit | 83.22 | 84.24 | 80.86 |
| bz6-rewind-replay (probe = fold whole world from empty) | rewind | 99.81 | 118.77 | 99.30 |
| bz6-rewind-ckpt (probe = checkpoint restore + 1024-entry replay) | rewind | 83.17 | 84.28 | 80.57 |

The prediction is CONFIRMED for the rewind path and REJECTED for the
edit path at this window size:

- **Rewind (long history): confirmed.** The logo-pattern probe —
  rebuild the world by folding `entries[0..tip]` from empty, 100k
  object allocations included — costs **99.8 ms vs 83.2 ms** for the
  checkpointed restore (**1.20×, +16.6 ms median**), with a fatter
  tail (p90 118.8 vs 84.3; max 213.7 vs 100.4 — the allocation churn
  shows up as GC). The checkpointed restore sits exactly at the
  measured draw floor (83.2 ms — the same median every non-rewind op
  reads), i.e. its model work (one shared-snapshot restore + a
  1024-entry replay) is fully hidden under the repaint; the naive
  probe's whole-world fold is not. Checkpoints here are FREE to
  maintain per the plain-data rule (an immutable Map reference), so
  the candidate wins its measured comparison outright.
- **Edit (re-fold-all vs incremental): rejected on data.** Re-folding
  all 24 window entries per edit vs only the edited entry's fold:
  **83.23 vs 83.22 ms median — a 0.01 ms delta (< 0.02%), inside
  run-to-run noise** (means 81.13 vs 80.86). At a 24-entry window the
  fold is ~24 × 8 field prints ≈ microseconds — the measured op is
  the copy-on-write table update + the double view derive + drawn-DOM
  sync, exactly the BZ4 finding's shape (the draw, not the recompute,
  is the cost). The §4.3 hazard is real only where the folded surface
  is the WHOLE environment (the logo demo folds every log entry every
  repaint); a windowed inspector never re-folds more than it draws.

### Candidates evaluated on the §4.3 row

- **Checkpointed rewind — ADOPTED (T).** Measured above: restores the
  probe target from a shared immutable snapshot + replays ≤ 1 024
  entries; ends at the exact pre-probe state (contract-pinned round
  trip). The one caveat the data surfaces: under plain-data rules the
  checkpoint's VALUE is avoiding 100k allocations + 3 072 skipped
  entries, not avoiding table copying (the restore still materialises
  a fresh 100k-entry table — a persistent/cherry-style structure that
  also removed the copy would attack the remaining floor, out of
  this lane's scope).
- **Incremental fold — REJECTED as the measurable lever at 24 rows
  (T); adopted structurally anyway (D).** The cache is what bounds
  every edit op to ONE fold recomputation (the contract the next
  window size or a full-environment fold would need), and it keeps
  the drawn window correct by construction — but the measured delta
  at this scale is noise, so the lane rejects the claim that it is
  BZ6's perf lever on this wire. The lever with data behind it is
  the checkpointed rewind.
- **Lazy tree — REJECTED on scope + data (U/D).** A lazily-materialised
  object tree attacks the 100k-table cost the build op pays once
  (175 ms untimed setup) and the copy-on-write per edit — but the
  timed interactions never touch more than the window (24 entries),
  so there is no measured scenario in which laziness changes a
  median; the sparse-table-plus-window pattern already achieves the
  viewport effect without it.
- **Worker with kill switch — REJECTED on scope (U), logo precedent
  recorded.** The harness measures in-process dispatch→paint clicks
  (the logo kill-switch worker exists for genuinely off-thread
  interpretation, src/examples/logo/worker*.ts); none of the §4.3
  BZ6 ops (field edit, fold, checkpoint restore) is an off-thread
  candidate — they are all bounded table work the main thread must
  see through the plain-data state. Building a Worker wire for an op
  with no measured main-thread overrun would be scaffolding, not
  measurement.
