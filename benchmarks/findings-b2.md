# Keyed DOM reconciliation bench findings (B2)

Scenarios for the add-keyed-dom-reconciliation change (tambor-ap8, roadmap
Gate B / bench B2). Results in `benchmarks/results/b2-keyed-churn.json`
(gitignored — regenerated by `node benchmarks/run.mjs --scenario
b2-keyed-churn`). Provenance rule per PR-01: the baseline below was recorded
BEFORE the keyed splice mechanism lands (task 5.0 completes before task 2.1).

## B2 — reorder/insert/remove churn on a memo-stable keyed list (task 5.0 baseline)

App: `src/examples/bench/keyed-table.ts` — demo `keyed-table`; scenario
`b2-keyed-churn` in `tests/e2e/bench-scenarios-b2.ts`; results
`benchmarks/results/b2-keyed-churn.json`.

Setup: "Build 1000" (untimed drawn setup — 1,000 memo-stable rows keyed by
id via `components.memo`), then a cycling churn set, one op per timed
sample: **Swap Rows** (reorder), **Insert first** (the mid-list insert — a
fresh row at position 0 shifts every subsequent row, the case the keyed
splice exists to kill; the tail-append case is M1's already-cheap B3 anchor
and is deliberately NOT the insert vehicle), **Remove 10** (remove), and
**Replace 10%** (the relabel control — rows at and after each relabelled
index change content, so they must rebuild under either rule). 8 timed ops
= two churn cycles, +1 untimed warmup op. `countMutations: true` — the
MutationObserver counts mutated elements with added/removed subtrees
EXPANDED before counting (the rinv protocol), so wrapper churn cannot hide
behind a single container swap.

Baseline BEFORE the keyed splice mechanism (PR-01): commit `14a2f0c11`
(main, add-keyed-dom-reconciliation §1 landed — keyed() declaration + pure
reconcile plan, painter NOT yet keyed). Chrome 156.0.8078.4, CDP CPU
throttled ×4, 3 runs × 8 ops (+1 untimed warmup op), production bundle.

| metric | value |
|---|---|
| wall-clock median | 259.22 ms/op |
| wall-clock p25 / p75 / p90 | 233.32 / 293.66 / 328.90 ms |
| DOM mutations per op | **3 020–3 023, near-identical across all 24 ops** |

Reading: every churn op — even the two-row Swap — deterministically touches
~3 021 DOM nodes. The per-keyed-row cost is wrapper churn: today a keyed
wrapper is fresh per derive, falls through the unknown-node fallback, and
rebuilds its wrapper div per row per frame (the inner memo-stable span
splices through M1's positional rule, so CONTENT is never stale — the cost
is purely structural: ~3 fresh/moved nodes per row per frame). Wall-clock
variance is frame-timing noise; the mutation count is the invariant the
keyed re-run must move. Task 5.1 target: mutations drop to the structural
delta (a swap moves 2 row elements, an insert-first builds 1 fresh row and
moves 0, a remove drops the removed rows), with focus/selection
preservation verified in a real browser; the B3 streaming anchor and the
pinned state-equivalence contract stay green in both runs.

## Post-keying verdict (task 5.1 — after §2 lands)

Recorded after the keyed re-run at the same protocol: same machine, Chrome
156.0.8078.4, CDP CPU ×4, 15 runs × 8 ops (+1 untimed warmup op), commit
`7726fc7fc` (§1 keyed declaration + §2 painter splice + §4 selector + §5.1
container identity + §5.2 bench wiring landed).

| metric | baseline (pre-keying) | keyed |
|---|---|---|
| wall-clock median | 259.22 ms/op | 231.52 ms/op |
| mutations: Swap Rows | 3 018 | **19** |
| mutations: Insert first | 3 023 | **21** |
| mutations: Remove 10 | 3 023 | **19** |
| mutations: Replace 10% | 3 020 | **216** |
| DOM mutations per op (median) | 3 022 | **21** |

Target met: every churn op now measures the structural delta — a swap moves
the 2 displaced row elements (the other 17 nodes are the three unkeyed
control-band buttons/spacers, rebuilt per frame by M1's positional rule by
design), an insert-first builds 1 fresh row, a remove drops the removed
rows, and the Replace 10% control rebuilds only the ~100 relabelled rows
plus the control bands. Focus/selection preservation is verified separately
by `tests/e2e/keyed-focus.spec.ts` (§5.1).

Two protocol fixes landed with the measurement (both in
`tests/e2e/bench-scenarios-b2.ts` / harness, not the mechanism):

1. **The scenario clicks `drawnOps`, not `pointsOf`.** "Replace 10%" is a
   band's second button; the in-process replay point for a non-first
   button falls inside the drawn first button's box (tambor-54j.17), so
   the replay-coordinate click fired **Build 1000** instead — every
   replace sample measured a full ~2 019-element rebuild (2 els × 1 000
   rows + bands) that has nothing to do with the keyed mechanism. The
   first keyed re-run recorded this artifact (replace = 2 019, median
   2022); `drawnOps` clicks the drawn button's live DOM box (drive.ts
   `clickDrawnText`, tambor-54j.13/.17 ground truth).
2. **The kept keyed box no longer re-appends to a same parent.** The box
   is a persistent child of the draw target; re-appending it every frame
   fired a childList move whose re-added subtree the expanded-mutation
   counter counts again (~1 005 elements/op even with splices intact).
   The box now adopts in place (`adoptOrAppend` same-parent guard) and
   the keyed container's order pass restores exact childList order with
   `insertBefore` moves only where the order actually changed.

Order-exactness stays contractual: the §2 suite pins that a keyed draw
builds identically to the unkeyed shape (same childList order), so the
placement pass is order-exact minimal-move, not append-only.
