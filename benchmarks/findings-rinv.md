# Runtime-invalidation bench findings (RINV)

Scenarios for the add-runtime-invalidation change (tambor-1cr). Results in
`benchmarks/results/rinv-*.json` (gitignored — regenerated by
`node benchmarks/run.mjs`). Provenance rule per change proposal PR-01: the
baseline below was recorded BEFORE the invalidation optimization landed.

## RINV — streaming tail in a memo-stable history (task 4.1 baseline)

App: `src/examples/bench/stream-dashboard.ts` — demo `stream-dashboard`;
scenario `rinv-tail-1msg` in `tests/e2e/bench-scenarios-rinv.ts`; results
`benchmarks/results/rinv-tail-1msg.json`.

Setup: Build 1000 history (500 tickers, msgs 1000, deterministic fold), then
"Stream 1" delivers exactly one new message per op — the smallest possible
tail mutation. Expected-text guard: `tickers 500 msgs 1013` (1000 + 1 warmup
+ 12 timed ops). `countMutations: true` — the bench installs a MutationObserver
over `#demo` (childList + characterData + subtree, installed after
setup + warmup, drained outside the timed window) and counts mutated elements
with added/removed subtrees EXPANDED before counting, so a full-tree rebuild
cannot hide behind a single wrapper swap (added/removed roots are expanded to
their leaf rows).

Baseline BEFORE the invalidation optimization (PR-01): commit `e12a2f06e`
(main, post add-frame-coalescing + add-resource-scopes/authored changes).
Chrome 156.0.8078.4, CDP CPU throttled ×4, 3 runs × 12 ops (+1 untimed warmup
op), production bundle.

| metric | value |
|---|---|
| wall-clock median | 281.24 ms/op |
| wall-clock p25 / p75 / p90 | 265.18 / 298.66 / 314.61 ms |
| DOM mutations per op | **4 054 — identical across all 36 ops** |

Reading: one streamed message deterministically touches 4 054 DOM nodes —
the full 500-row tree is rebuilt and re-spliced for every op (the flat
per-op cost findings-bz.md pinned at the whole-view layer, now quantified at
the mutation level). Wall-clock variance is frame-timing noise; the mutation
count is the invariant the optimization must move. Task 4.2 target: mutations
drop to the changed tail rows (single digits per op) while the pinned
state-equivalence contract stays green; wall-clock is expected to drop with
the mutation count but the mutation count is the honest comparison (the
frame-batched wall clock at 60 Hz bounds it regardless).

## Post-optimization verdict (task 4.2, add-runtime-invalidation landed)

Re-run at the same protocol after §1-§4 landed (whole-view short-circuit,
per-child identity reuse, per-ticker composed-wrapper memo in the demo):

| metric | baseline (pre) | post |
|---|---|---|
| wall-clock median | 281.24 ms | 232.3 ms |
| DOM mutations per op | 4 054 | **31 — stable across all 36 ops** |

The 31 = the one changed ticker's fitted labels + the fresh summary line +
the re-ranked book line — the changed rows, exactly the tasks.md 4.2 target
(a 130× reduction from the baseline). The mutation metric semantics were
corrected during this task: the counter reconciles removals at batch end so
per-child reuse splices (re-parented existing nodes) are excluded and only
newly created elements and altered text count (see the observer comment in
tests/e2e/bench-apps.bench.ts). Wall-clock moves less than the mutation
count because the frame-batched paint already amortized the rebuild; the
mutation count is the honest comparison.

Two demo-side increments were required for the drop, both in
`src/examples/bench/stream-dashboard.ts` (the render-layer machinery alone
cannot help a view that derives fresh Elem identities per frame):
(1) a per-app row memo keyed by ticker id + drawn line (unchanged lines
return the previous fitted labels); (2) the rows composed as per-ticker
translate wrappers owned by the memo (a fresh wrapper per row would itself
be a counted mutation — the counted elements were the layout wrappers, not
the rows). Drawn output verified identical (per-label y positions equal to
the flat verticalLayout path over randomized trials).
